# Relay 黑客松需求评审纪要

> 日期：2026-08-29  
> 评审对象：Relay PRD v1.0  
> 参会角色：产品负责人、反方产品经理、用户研究、UI/UX、前端/技术负责人、安全、QA/路演、商业  
> 最终产出：PRD v1.1、Demo 规格、ADR-001

## 1. 需求校准

原问题“这个应用能不能做、用什么技术做”被改写为：

> 在单人 Web 开发、48～72 小时、黑客松重视视觉和现场可靠性的条件下，Relay 应用哪一个可演示场景证明女性生活管理负担的价值？实现到什么程度既诚实又足够有竞争力？哪些能力必须进入 P0，哪些应延后？

本次会议不评审 Relay 是否已经成为可商业化的大平台，只评审黑客松 Demo 是否值得做以及如何降低失败概率。

## 2. 使用的评审框架

评审吸收了几个公开 GitHub 提示框架的结构，但没有安装或照搬完整提示包：

- [Kiro role-based / validation-oriented prompting](https://github.com/jasonkneen/kiro/blob/main/spec-process-guide/prompting/strategies.md)：让产品、设计、技术从各自约束出发，并显式比较取舍；
- [OpenAI spec compliance reviewer](https://github.com/openai/plugins/blob/main/plugins/superpowers/skills/subagent-driven-development/spec-reviewer-prompt.md)：检查缺失需求、误解和过度设计，不相信“看起来已经完成”；
- [Senior PM PRD prompt](https://github.com/wwwazzz/senior-pm-prompt)：使用目标—需求—验收映射和 Review Notes；
- [Product Manager Prompts submission guide](https://github.com/deanpeters/product-manager-prompts/blob/main/SUBMISSIONS-GUIDE.md)：评审在解决真实问题的同时解释 PM 思考方法，并把假设单独列出。

本次采用的统一问题：

1. 这个场景在 90 秒内能证明什么？
2. 哪些证据支持它，哪些仍是假设？
3. 每项 P0 对评委有什么可见价值？
4. 技术能力与验收标准是否一致？
5. 是否存在更简单、风险更低的实现？
6. 用户是否知道责任和边界？
7. 演示失败后能否恢复？

## 3. 第一轮：各角色独立立场

### 产品负责人

> 今天不是评审 Relay 能不能成为大平台，而是判断一次责任变化能不能让评委看见用户真正减负。宏观市场、价格和未来功能不能抢占核心闭环。

立场：场景可以继续，但要把 P0 缩减约 40%。

### 反方产品经理

> 独居增加和女性照护负担证明问题重要，却不能证明年轻女性每周会频繁把生活事项交给别人。这个产品需要用户同时拥有可信协作者，真实目标人群比“城市年轻女性”更窄。

立场：作为 Demo GO；作为已验证商业产品暂时 NO-GO。

### 用户研究

> 没有现成证据证明三件事：跨人事项足够高频、微信摩擦大到值得打开新链接、用户愿意持续付费。路演只能称其为“值得验证的产品缺口”。

立场：保留日记研究和真实分享率验证，不把价格点击当购买。

### UI/UX 负责人

> 风格不能停留在米白、紫色、圆角卡片，否则仍是普通生活方式 SaaS。必须建立一个品牌级符号：责任轨道。责任点从林然移动到小雨，才是产品差异的可见证据。

立场：五个核心界面状态足够；必须增加双手机 `/demo` 路演舞台。

### 技术负责人

> React、Vite、Tailwind 和动效库不过度；过度的是同时做 localStorage、匿名 Auth、RLS、Edge Function、令牌、Realtime、乐观锁和离线切换。评委看不到这些复杂度，却会直接看到前端粗糙或演示中断。

立场：P0 使用确定性本地架构；Supabase 仅为 Stretch Goal。

### 安全负责人

> 如果来不及正确实现 Edge Function 和 RLS，不能为了“像真后端”而公开匿名写权限。Demo 只用虚构数据，并明确本地分享不等于生产安全。

立场：安全能力要么正确实现，要么明确延后，不能做半套。

### QA / 路演负责人

> 现场只保证一条黄金路径连续跑十次：载入故事—生成事项—小雨接受—责任变化—完成—重置。固定状态跳转和录屏是正式可靠性设计，不是临时补救。

立场：正式演示不依赖网络、扫码、打字或远程素材。

### 商业负责人

> 当前最可信的商业叙事是“事件获客—成功接棒—关系复用—发生重复协作—再验证订阅”，不是四档价格表。

立场：价格保留在研究章节，不进入主演示。

## 4. 第二轮：交叉质询

### 议题 A：交接的是任务还是责任？

产品：如果只是发送 checklist，Relay 与待办差异不足。  
设计：责任必须持久可见，同时允许拒绝。  
安全/伦理：宠物主人不能把医疗决策“负责到底”交出去。  

决议：P0 展示“有边界的当前执行责任”。小雨负责带布丁完成本次复诊，但手术、住院、方案变化和重大费用仍联系林然。

### 议题 B：是否保留“协助一步”和“完整接棒”？

设计的初始意见：两者有助于表现产品成熟度。  
产品与技术：两套语义会让状态、权限、文案和测试量接近翻倍，90 秒也无法解释。  

决议：P0 只做一种有边界的接棒；有限协助进入 P1。设计的不同意见记录在案，但服从时间约束。

### 议题 C：是否需要真实跨设备分享？

产品：真实分享很有说服力。  
技术：localStorage 无法跨设备；完整 Supabase 会挤压视觉时间。  
路演：现场扫码、联网和等待会破坏节奏。  

决议：P0 用 `/demo` 双手机舞台和同源标签页同步，明确是交互原型。核心完成后若剩半天，再实现极简 Supabase。

### 议题 D：怎样避免看起来像 Kanban？

设计：颜色和列名不够；每张卡必须把责任轨道置于标题之后的第二层。  
产品：状态语言需要统一。  

决议：首页统一为“需要我推进 / 等待对方回应 / 已有人接住”；“压着我”只用于旁白和负荷描述。

### 议题 E：预置数据应该有多少？

产品：数据要证明三个状态和可信关系。  
设计：太多卡会让动效离开视口。  
技术：日期必须相对生成，数据需要版本化和可重置。  

决议：一个英雄事项加四个辅助事项；每条数据承担明确叙事任务。

## 5. 可行性结论

| 维度 | 评分 | 结论 |
|---|---:|---|
| 黑客松演示力 | 8/10 | 责任变化具备强视觉前后对比 |
| 女性主题关联 | 8/10 | 通过隐形管理负担、拒绝权和最小共享表达 |
| 用户痛感 | 7/10 | 问题成立，实际频率仍待一手研究 |
| 场景频率 | 5/10 | 事件型主演示不能直接证明日常留存 |
| 差异化 | 6/10 → 8/10 | 加入边界与责任轨道后更清楚 |
| 48～72 小时可行性 | 原方案 5/10 → 新方案 9/10 | 砍掉生产级后端与双模式 |
| 商业可信度 | 4/10 | 暂不主讲定价与收入规模 |

最终结论：

- 女性黑客松 Demo：**GO**；
- 已验证独立商业产品：**尚未达到 GO 条件**；
- 开发前提：按 v1.1 P0 执行，不重新把 P1 功能带回主演示。

## 7. 被删除或延后的需求

P0 删除：关系圈 CRUD、真实账号、真实跨设备同步、Realtime、PWA、通用 AI 解析、文件上传、完整事项 CRUD、价格页、每周检视、复杂活动日志和乐观锁。

P1：Supabase 极简分享、有限协助、调整/撤回/过期、关系圈、通知和价格假门。

生产阶段：身份升级、完整 RLS、令牌摘要、审计、速率限制、敏感信息治理和数据导出。

## 8. 产品经理小白学习笔记

### 8.1 一次正式评审在做什么

需求评审不是大家一起增加功能，而是一起减少错误投入。会议应按以下顺序：

```text
确认要证明什么
→ 各角色暴露风险
→ 对争议给出备选方案
→ 明确取舍
→ 回写需求与验收
→ 保存决策理由
```

### 8.2 各角色的责任

| 角色 | 主要负责 | 不应被误解为 |
|---|---|---|
| 产品经理 | 用户问题、范围、优先级、成功标准 | 只写功能清单 |
| 设计师 | 旅程、信息层级、理解成本、情绪安全 | 只配色和画图 |
| 工程师 | 实现方案、风险预算、替代路径 | 只回答能不能做 |
| QA | 状态、边界、恢复与验收 | 开发结束后才找 bug |
| 用户研究 | 证据、假设和验证方法 | 用宏观报告替代用户 |
| 商业 | 谁付费、为什么、何时验证 | 先编一个漂亮价格 |

### 8.3 应特别注意的十件事

1. 宏观趋势不能直接证明功能频率和付费；
2. 先定义 Demo 要证明什么，再决定页面；
3. 产品需求与技术方案不是同一层；
4. “发一个链接”隐含身份、权限、同步和隐私；
5. 双边产品要分别评审两种用户；
6. 工程范围问题也是产品优先级问题；
7. 设计需求应改写成可测试标准；
8. 预置数据是剧本，不是占位符；
9. 模拟能力必须诚实标注；
10. 没有落入 PRD、ADR 或验收项的会议结论等于没有决定。

### 8.4 如何写一条好需求

较弱：

> 做一个很好看的接棒页面。

可执行：

> 协作者在 20 秒内无需讲解即可说出目的、时间、步骤、完成标准和责任边界；首屏不出现注册、会员或其他事项；关键按钮不小于 44px。

较弱：

> 分享状态要实时同步。

可执行：

> P0 的两个同源标签页通过 BroadcastChannel 在 500ms 内同步；P0 不承诺不同设备同步，真实远程同步属于 Stretch Goal。

## 9. 假设与后续验证

- 目标人群每周存在足够多跨人事项；
- 单事项链接比微信反复解释更省力；
- 协作者愿意点击外部链接；
- “责任轨道”比普通状态标签更易理解；
- 成功接棒会带来关系复用；
- 用户最终愿为自动化和长期沉淀付费。

这些假设不由本次会议证明，继续按 PRD 第 19 章进行一手验证。
